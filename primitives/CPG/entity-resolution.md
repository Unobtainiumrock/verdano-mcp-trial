# Entity Resolution — bipartite matching with stratified evidence

The CPG layer's first job is **mapping retailer-published identifiers to ERP-canonical identifiers** without a shared primary key. This applies to:

- **Products** — retailer SKU / GTIN / free-text name → ERP `sku`.
- **Locations** — retailer depot string → ERP `ship_to_location_id`.
- **(Implicit) Time periods** — addressed in [`demand-alignment.md`](demand-alignment.md), not here.

This is the **bipartite mapping graph** primitive surfaced by Gemini ([`raw-truth.md`](../../docs/process/raw-truth.md) iteration 4 §"The CPG Primitives" #1), extended with explicit evidence stratification.

## Core structure

For each kind of entity (products, locations) we have two disjoint vertex sets:

- $V_R$ — identifiers as published by the retailer (Tesco's `tesco_item`, Sainsbury's `gtin` + `item_name`, etc).
- $V_E$ — identifiers in the ERP master (`sku`, `ship_to_location_id`).

We construct a bipartite graph $G = (V_R \cup V_E, E)$ where each edge $e \in E$ carries:

- A **confidence weight** $w(e) \in [0, 1]$.
- An **evidence record** — *which rung of the resolver fired* and *what value matched*. This is the audit-trail / provenance dimension.

See [`docs/architecture/formalism.md`](../../docs/architecture/formalism.md) §3 for the formal definitions.

## Stratified evidence — the resolver fall-through

A single bipartite edge isn't generated by a single matching procedure. It's generated by a **priority-ordered cascade**: the first rung that fires produces the edge. Each rung carries its own confidence range.

For products, the cascade is:

| Rung | Source | Trial-scope score (per-match, dynamic) | Notes |
|---|---|---|---|
| $E_1$ | Exact match on `current_gtins` | $w_1(x) = (1 - \epsilon) / K_x$ | Fellegi-Sunter posterior; $K_x$ = collision count for matched GTIN. Cascade fires first; preempts $E_2/E_3/E_{3b}/E_4$ on hit. |
| $E_2$ | Exact match on `legacy_gtins` | $w_2(x) = (1 - \gamma)(1 - \epsilon) / K_x$ | Adds obsolescence penalty $\gamma$ for legacy-points-to-superseded-SKU risk. Berry Smoothie test fixture. |
| $E_3$ | Exact match on `aliases` (after `_norm`, including size-unit canonicalization) | $w_3(x) = (1 - \epsilon) / K_x^{\alpha}$ | Dampening exponent $\alpha > 1$ penalizes overloaded generic aliases. Tom Basil Soup 0.5kg ↔ Tomato Soup 500g matches via D-013 size normalizer. |
| $E_{3b}$ | TF-IDF token-overlap, score $\geq \tau_{\text{tfidf}}$ | $w_{3b}(s, P) = \text{tfidf}(s, P) \cdot (1-\epsilon) / K_x^{\alpha}$ | Per **D-013**. IDF-weighted partial-token match using ERP-master vocabulary as corpus. Catches "Falafel Bowl"-style cases where retailer string shares rare tokens with multiple products → K_x captures ambiguity cleanly. Default $\tau_{\text{tfidf}} = 0.5$. |
| $E_4$ | Fuzzy match on canonicalized name | $w_4(x) = \mathrm{JW}(x)^2$ | Jaro-Winkler² (per D-011). Last-resort fuzzy when none of the above fire. |

**Hyperparameter defaults (initial, tunable once labels arrive):**

- $\epsilon = 0.02$ — global retailer-data-corruption prior.
- $\gamma = 0.10$ — legacy-GTIN obsolescence rate.
- $\alpha = 1.5$ — alias-collision dampening exponent.

> **Bands no longer enforced.** Per Gemini iteration 9 (locked), strict non-overlapping bands per stratum are abandoned. The cascade is a *discovery* heuristic (which stratum fires first); the *score* is the per-match Fellegi-Sunter posterior (or JW² for fuzzy), reflecting the actual probability of correctness. See "Resolved (b)" below.

### Worked example — what the formulas produce on realistic ambiguity

Assuming an ERP master with $N = 200$ SKUs, $1\%$ GTIN collision rate, $5\%$ alias overlap, and the default hyperparameters:

| Scenario | Match | $K_x$ | Score | Outcome |
|---|---|---|---|---|
| A | Unique current GTIN | $1$ | $w_1 = 0.98$ | Auto-allocate. |
| B | **Colliding** current GTIN | $2$ | $w_1 = 0.49$ | **Drops out of auto-allocate band**, surfaces for review. (Static band $[0.95, 1.0]$ would have silently auto-mapped to a random variant.) |
| C | Unique legacy GTIN | $1$ | $w_2 = 0.88$ | Auto-allocate (depending on tripwire). |
| D | Generic alias ("Spicy Chorizo") on 3 SKUs | $3$ | $w_3 = 0.18$ | Review queue. The dampening exponent crushes confidence on overloaded aliases. |

This is the operationally important consequence: the same exact-match procedure produces *different* scores depending on the master's empirical ambiguity. No band-tuning required — the data does the work.

### Implementation hint

Pre-compute the frequency dictionary $K_x$ for every key in the ERP master at adapter startup (one pass over `GET /erp/products`). On a match at any stratum, look up $K_x$ and apply the corresponding formula. No labeled data, no tuning, no static bands. See `primitives/CPG/entity-resolution.md` cross-references.

The `MappingResult.evidence` field captures which rung fired and the input value. Confidence-band cross-checks (e.g., retailer-declared `temperature_band` ≠ ERP `temperature_band`) **multiply confidence by a penalty factor** before final assignment.

## Three review states (not two)

A subtle point Gemini's framing collapses but the system needs to distinguish:

| State | Graph condition | Operator action |
|---|---|---|
| **Resolved** | Edge with $w \geq \theta_{\text{auto}}$ exists | Auto-accept; pass through to allocation. |
| **Needs verification** | Edge exists but $w < \theta_{\text{auto}}$ | Show the candidate to the operator; ask "yes/no". |
| **Unmapped** | No edge generated by any rung | Show the operator the un-mappable retailer line; ask them to *create* a mapping. |

Gemini's text framed both as "ambiguous mappings" but they're operationally distinct: the second case has a candidate to verify; the third has no candidate at all. The review-queue surface should preserve that distinction.

## Confidence calibration — what's locked, what's open (per D-011)

### Locked: $E_4$ (fuzzy) scoring

Use **Jaro-Winkler similarity** as the underlying string-distance measure (canonical for short record-linkage; weights prefix matches heavily — appropriate because retailer SKU strings tend to lead with brand or category tokens that carry signal). For Jaro-Winkler similarity $x \in [0, 1]$, set

$$w_{\text{fuzzy}}(e) = x^2$$

The squaring suppresses mid-tier "vibes-y" matches and creates a starker contrast between true matches and noise. (Gemini iteration 5 also suggests $x^3$ as an aggressive variant; use $x^2$ as default and tune if needed.)

### Locked: production calibration path

Once a labeled stream of operator review resolutions exists ($N \gtrsim 200$), upgrade to **Platt scaling (logistic regression)** over a multi-feature input:

- Jaro-Winkler similarity (the current scalar)
- Token-overlap (TF-IDF weighted)
- Vertex degree in the bipartite graph (penalty for many-to-one ambiguity)

At $N \gtrsim 1000$, **isotonic regression** becomes feasible. **Beta calibration** is the natural alternative for inputs already bounded in $[0, 1]$.

### Resolved (a): Fellegi-Sunter unsupervised posteriors per stratum

**Locked via Gemini iteration 8.** Exact-match scores are per-match dynamic posteriors derived from the empirical collision count $K_x$ and three unsupervised priors ($\epsilon, \gamma, \alpha$). Formulas above. The static-band question dissolves under this framing — there are no bands, only data-driven probabilities.

The standard published reference is **Fellegi-Sunter (1969)**, "A theory for record linkage". The key insight: the $u$-probability ($P(\text{agreement} \mid \text{non-match})$) can be computed exactly from the master's collision rate without supervision, while the $m$-probability ($P(\text{agreement} \mid \text{match})$) is conservatively assumed $\approx 1$ for exact-match strata. Modern variants relax these assumptions when supervised data is available.

### Resolved (b): drop strict bands — cascade is a *blocking strategy*, scoring is independent

**Locked via Gemini iteration 9.** Strict non-overlapping confidence bands per stratum are abandoned. The cascade ($E_1 \succ E_2 \succ E_3 \succ E_4$) governs **discovery order** — which generator fires first, with lower strata preempted on a hit — but does **not** constrain the resulting score. Each stratum produces a probability on its own merit. An unusually clean $E_4$ match (e.g., Jaro-Winkler $0.98$ on a highly-specific string) can legitimately score above an ambiguous $E_3$ match (e.g., exact alias on an overloaded generic name like "Vegan Patty"). The score-ordering inversion is not a bug; it's the system reporting what the data says.

The standard published framing is **Cascaded Classification** (record-linkage literature): in the supervised production calibrator, the stratum joins the feature vector as a one-hot indicator. The LR learns negative weights for the lower strata so an $E_1$ baselines higher than an $E_4$ in expectation, while still allowing the data-driven overlap.

#### UX consequence: separate Lineage from Confidence

The review-queue surface displays **two distinct fields per match**:

| Field | What it shows | Example |
|---|---|---|
| **Lineage** (categorical) | Which stratum generated the candidate | `[Tag: Exact GTIN]`, `[Tag: Fuzzy Alias]` |
| **Confidence** (numeric) | Raw probabilistic score, un-banded | `Confidence: 92%` |

Operators see "this is a fuzzy match" and "the system trusts it 92%" as orthogonal facts. A 92% fuzzy match outranks a 65% alias match in the auto-allocate decision; the operator understands why because the lineage is visible.

#### Tripwire: globally unified at production scope

Once the LR has produced calibrated probabilities, the auto-allocate tripwire is a **single global threshold** on `confidence` (no per-stratum thresholds). E.g., $\theta_{\text{auto}} = 0.90$.

**Trial-scope nuance (pushback on Gemini):** the unified-threshold benefit is conditional on having *calibrated* probabilities. At trial scope we have only crudely calibrated scores (Jaro-Winkler² for fuzzy; band-derived collision-rate baselines for exact, pending follow-up A). A single global threshold at trial scope is therefore more conservative than at production scope — treat $\theta_{\text{auto}}$ as `provisional` until calibration data accumulates.

## Connection to the canonical entity model

The mapping graph corresponds to the `RetailerToErpMapping` entity in [`docs/architecture/verdano-problem-entity-model.md`](../../docs/architecture/verdano-problem-entity-model.md), with the `MappingEvidence` table holding per-edge evidence records. The fall-through rungs are *not* a hard-coded sequence — they're declared in the retailer adapter spec (per **D-001** config-driven adapters), so different retailers can have different rung orderings if needed.
